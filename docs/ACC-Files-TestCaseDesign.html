1 TC-ACC-01 Account with NO project access cannot see or use the project A test account that is not a member of the project must not even see the project, so it can never reach the upload / delete / restore flow.

Pre-condition: provision a test account with NO membership / access to the target project.

  1. Sign in with that account.
  2. Look for the project in the project list / home; also try the assignment deep-link directly.
  • The project is not listed for this account.
  • Opening the deep-link is rejected (no access / not found).
  • There is no path to the folder, therefore no upload / delete / restore is possible.

  1. Sign in and open the naming-standard folder.
  2. Inspect the Action Bar / row menu for Upload, drag-and-drop, and any upload deep-link.

5 TC-ACC-05 Create + Upload permission can upload files A member granted the 'Create + Upload' folder-permission level (below Edit) can reach the folder and perform an upload — per the documented model, 'Upload files / Upload to a folder' is granted at the Create + Upload level and above.

Pre-condition: provision a test account with 'Create + Upload' folder permission on the project / folder.

6 TC-PRM-01 Delete / Restore permission matrix — every role

Test condition: Across 3 permission levels — Project Admin (Manage), Editor (Edit), Read-only (View) — each attempting Delete and Restore. (Upload permission is covered separately by TC-ACC-01..05.)

Delete and Restore are file actions granted at the Edit level and inherited by Manage (Project Admin); they are NOT available at View-only levels. This case verifies Delete/Restore availability across roles — upload is intentionally excluded to avoid overlap with the TC-ACC upload cases.
  1. For each role (Project Admin / Manage, Editor / Edit, Read-only / View), attempt: delete a file and restore a file.
  2. Record for each combination whether the action is available in the UI and whether it succeeds server-side.
  • Project Admin (Manage): Delete and Restore both allowed.
  • Editor (Edit): Delete and Restore both allowed (Restore requires Edit level — see help docs).
  • Read-only (View): Delete and Restore both blocked (hidden/disabled in UI and enforced server-side).
 Functional P1
7 TC-PRM-02 Delete & Restore require Edit (or higher: Project Admin); no Edit/Manage → blocked

Test condition: Users WITHOUT Edit/Manage permission (View-only / View+Download / Create+Upload) vs users WITH Edit (Editor) and WITH Manage (Project Admin). Each attempts Delete and Restore.

Per the documented permission model, Delete and Restore are file actions granted at the Edit level and inherited by Manage (Project Admin has Manage on all folders by default). A user with neither Edit nor Manage cannot perform them.
  1. Sign in as a user with neither Edit nor Manage permission (e.g. View-only or Create+Upload).
  2. Attempt Delete from the row menu and Restore from Deleted Items.
  3. Sign in as an Editor (Edit) and repeat both operations.
  4. Sign in as a Project Admin (Manage) and repeat both operations.
  • Without Edit/Manage: Delete and Restore are hidden or disabled; server rejects direct attempts.
  • With Edit (Editor): Delete and Restore both succeed.
  • With Manage (Project Admin): Delete and Restore both succeed — Admin inherits edit-level file operations.
  • Reference: Project Member Folder Permission Levels (Delete / Restore at Edit level; locked files cannot be deleted — TC-DEL-04).
 Functional P2
8 TC-DEL-04 Delete a locked file is blocked

Test condition: Target file is LOCKED by another user.

A file locked by another user cannot be deleted, regardless of the acting user's permission.
  1. Open a file locked by another user → attempt Delete.
  • Delete action is disabled / blocked with an explanatory message.
 Functional P2

41 TC-NET-02 Failure — Server error responses (500 / 502 / 503 / 504) when Upload is clicked The Upload-stage server check fails with each common server / gateway error code in turn (500, 502, 503, 504); all four must surface an explicit failure and offer the same Retry path.
  1. Fill all 11 attributes with valid values.
  2. For each status code in turn (500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout): simulate the server returning that code (proxy/mock, e.g. Playwright route fulfil), then click Upload.
  3. Observe and record the error surface for each code — message wording, whether Retry is offered, whether the dialog stays usable.
  4. Restore the server (remove the mock) and click Retry; confirm the upload completes.
  • For every one of 500 / 502 / 503 / 504: Upload fails with an explicit error — files can't be added to the Files tool (documented Upload-stage failure).
  • Failure handling is CONSISTENT across the four codes: no silent hang, no stuck progress bar, no blank/broken error surface; a Retry option is offered in all four.
  • After server recovery, Retry completes the upload; no duplicate or partial file is created by any failed attempt.
  • Record any difference in wording between codes (e.g. 503 'service unavailable' vs 504 'gateway timeout') — differences are a finding, not a failure.
 Functional P2

47 TC-DEL-01 Workflow — Delete a compliant file Delete a file via the row menu / Action Bar Delete, then confirm it moved to Deleted Items. Row selectability is verified here as part of the delete flow (no separate list-only case).

Pre-condition: the project folder already contains a compliant .txt file (uploaded per TC-UPL-01).

  1. In the Files list, select the uploaded file's row via its checkbox — the row highlights and the Action Bar reacts.
  2. Open the row's '…' (More) menu → Delete (or use the Action Bar Delete).
  3. Confirm in the Delete dialog.
